# 图章.exe 逆向分析报告

> 目标：`D:\杂乱工具\图章.exe`（1,292,800 字节，SHA-256 `c9bcbacd80cb46024a257883a9573dc7fc7791bd8b08a05a8ad27b62e42a3578`）
> 目的：摸清"印章/图章生成"的核心算法，为用现代技术重写做技术交底。**本次只分析，不重构。**
> 分级说明：**【确定】**= 静态/动态证据直接可见；**【高度怀疑】**= 多证据指向但未逐行验证；**【推测】**= 经验判断，需实测确认。

---

## 0. 一句话结论

它不是一个"图像滤镜"程序，而是一个**参数化矢量排版的印章生成器**：所有章型（圆/椭圆/方/菱形/三角）都来自同一个"外框路径 + 线宽"抽象，图符（五星/自定义 PNG）按外接圆内接几何生成，文字用"逐字定角度 + 逐字旋转"的环排算法铺在圆周上，最后用 GDI+ 抗锯齿栅格化，按用户设定的 DPI 导出 PNG/GIF/BMP/JPG/TIF。

**重写的技术难点不在算法复杂度，而在"参数到视觉的一致性"**——也就是几十个可调参数（线宽/半径/偏移/间距/字宽字高/角度）之间的耦合关系。

## 1. 样本与壳

### 1.1 文件结构【确定】

| 项 | 值 |
|---|---|
| 类型 | PE32 / x86 / Windows GUI，非 .NET（CLR 目录为 0） |
| 编译时间戳 | 1992-06-20 06:22:17（**假时间戳**，Delphi + 壳的典型特征） |
| 节 | `CODE` `DATA` `BSS` `.idata` `.tls` `.rdata` `.reloc` `.rsrc` `.sedwen` `.adata` |
| 入口点 | RVA `0x3d6001` → 落在 `.sedwen` 段（**壳段**） |
| 静态导入 | 仅 20 个函数（GetProcAddress / LoadLibraryA / VirtualAlloc / VirtualFree / CreateWindowExW …），imphash `23cac58dde7ab76ff5368157704dd92a` |

判定加壳的两条硬证据：

1. **段体积异常**：`CODE` 段虚拟大小 `0x2ed000`（3 MB），磁盘上只有 `0xfaa00`（1 MB）；`.rsrc` 虚拟 `0x9e000`，磁盘 `0x3b000`。
2. **壳段的自我修复逻辑**：`.sedwen` 里能看到 `VirtualAlloc(…,PAGE_EXECUTE_READWRITE)`、`GetProcAddress` 重建导入表，以及经典取基址手法：

```asm
; 0x139713 附近（文件偏移）
mov   esi, [esi]            ; 目标处 RVA
push  dword ptr [edi]       ; 保存原字节
mov   byte ptr [edi], 0C3h  ; 临时写成 RET
call  edi                   ; 调用 → eax = 返回地址 → 反推基址
pop   dword ptr [edi]       ; 还原原字节
```

解压器在 `.sedwen` 内（文件偏移 `0x139c6c` 起，三个子函数：建表 / 读头 / 主解码）。内部结构是 **canonical Huffman + LZ 匹配**：字节直方图 → 23 级码长上限 → `1<<24` 码空间校验 → 生成 `perm[]` 规范化表。**不是** zip/LZMA/bzip2 标准流（无 `PK`/`BZh`/`7z` 魔数），是壳自带的私有格式。

### 1.2 壳的运行时行为【确定】

壳**没有**把解压结果丢到新分配的堆块，而是**就地写回镜像自身**：程序跑起来后，`0x401000` 起的整段代码页变成 `PAGE_READWRITE`，`.rsrc` 段同样被就地解压。这让脱壳变得非常省事。

### 1.3 脱壳（已复现的方法）

1. 启动进程，等 3 秒让它自己解完；
2. `OpenProcess(PROCESS_VM_READ)` + `ReadProcessMemory(0x400000, 0x3DA000)` 一次性读整个镜像；
3. 按段表把"虚拟大小"当成"磁盘大小"重排文件布局，重建一个可直接静态分析的 PE。

> 产物：`证据/unpacked.exe`（3,958,784 字节，可正常被 objdump/IDA 识别）
> 脚本：`证据/脱壳脚本_dumper.py`
> 校验点：脱壳后 `.rsrc` 里的窗体资源变成可识别的 DFM 二进制（`TPF0` 签名），说明资源也解压成功。

## 4. 核心算法

### 4.1 单位与坐标【高度怀疑】

代码里大量出现整数像素运算 + `fildl`（整数转浮点）后再做三角运算，说明内部以**像素整数**为参数、绘制时转浮点。DPI 参与"最终像素尺寸"换算，而不是在绘制过程中。
> 复现建议：内部统一用 mm 或 pt 的浮点，最后一步才乘 `dpi/25.4` 转像素——这是比原程序更干净的做法。

### 4.2 图符：正五角星的几何【确定，最强证据】

`0x6e56a4` 函数生成五角星 10 个顶点。它用到的两个常量是：

| 地址 | 类型 | 值 | 含义 |
|---|---|---|---|
| `0x6e5958` | 80 位扩展精度 | `0.3141592653589793` | **π/10 = 18°** |
| `0x6e5964` | 80 位扩展精度 | `0.9424777960769379` | **3π/10 = 54°** |
| `0x6e5970` | float32 | `2.0` | 用于 `x = 2·cx − x` 之类的镜像 |

核心计算（还原后的算式）：

```
r_inner = R · sin(18°) / sin(54°) ≈ 0.382 · R      ; 0x6e56b5–0x6e56d7
外顶点:  (cx ∓ cos(18°)·R,      cy ∓ sin(18°)·R)
内顶点:  (cx ∓ cos(54°)·r_inner, cy ∓ sin(54°)·r_inner)   ; 再按 72° 步进旋转出 5 组
镜像:    x' = 2·cx − x  (同样的 y)                          ; 由 2.0 常量完成
```

`0.382` 不是随便取的调参，而是**正五角星内接点的解析解**：内外半径比 `sin(18°)/sin(126°) = sin18°/sin54°`。所以：
- 重写时只需 5 个外点 + 5 个内点，交替连成闭合多边形，**不需要任何硬编码坐标**；
- 这也解释了说明里"图符为[五星]时，由圆心位置按半径伸缩显示正五角星"。

### 4.3 文本：环排（核心算法）【确定】

主流程在 `0x5fe10c`，逐字循环里最关键的是 `0x5fe1c2 – 0x5fe1f6`：

```asm
call   0x600e2c            ; eax = 当前字符序号 i
mov    esi, eax
and    esi, 07Fh           ; i 限制在 0..127（最多 128 字）
imul   esi, [eax+160h]     ; × 自.0x160  ← 每字角度步进 Δ（整数，单位: 度）
mov    eax, esi
cdq ; idiv 168h            ; ÷ 360  (0x168 = 360)
mov    eax, edx            ; 取余
add    eax, 168h ; idiv 168h
mov    esi, edx            ; 归一化到 [0, 360)
```

于是**每个字符的角度**：

```
a_i = (i × Δ) mod 360      (单位: 度, Δ 来自参数面板"每字角度/字距")
```

接着 `0x5fd99c / 0x5fd5d4` 把这个角度变成屏幕位置和字形旋转。同一段代码里反复出现同一套常量与运算，是典型的 **度→弧度 + 半字宽/半字高投影**：

| 地址 | 值 | 用途 |
|---|---|---|
| `0x5fd974` | `2.0f` | 取一半（半宽/半高） |
| `0x5fd978` | `π`（扩展精度） | 弧度换算 |
| `0x5fd984` | `180.0f` | 弧度换算 |
| `0x6ea10c / 0x6ea118 / 0x6ea124` | `2.0 / π / 180.0` | 另一条文本通道的同一套换算 |

还原出的定位式（`0x5fd80a – 0x5fd890`）：

```
rad = a_i · π / 180
origin.x = 基准x − cos(rad) · (字宽/2)
origin.y = 基准y − sin(rad) · (字高/2)      ; 再把两半投影相减得到最终原点
```

> 注意：这实际上是**把半宽/半高分别投影后相减的"近似旋转"**，不是标准 2D 旋转矩阵（标准式里 x 项应含 `+sin·h/2`）。重构时用标准旋转矩阵是对的，视觉上不会更差；但若要做**像素级还原**，就得照抄这个近似——标记为【高度怀疑】，需要输出对比图验证。

另有三处同类实现（`0x6e8e60` 附近）：按 `WideChar` 逐字遍历（`cmpw $0x20` 判断空格），**累加**角度与偏移。说明环排不是固定步进，还支持"按字累加"的连续排版模式——对应说明里的"平环排列方式"。

### 4.4 平排与环排的统一【推测】

两条路径共用同一套"字符 → (位置, 旋转角)"的数据结构，区别只在角度生成：
- 平排：角度恒为 0，位置按字宽累加（可带水平/垂直偏移）；
- 环排：角度 = `i·Δ mod 360`，位置由角度与环排半径决定。

### 4.5 文本之外的图形【确定 + 推测】

| 元素 | 实现方式 | 可信度 |
|---|---|---|
| 外框（圆/椭圆） | GDI+ 路径（`DrawEllipse` 等价）+ Pen 描边，线宽为 0 时不描边 | 高度怀疑 |
| 方/菱形/三角 | 同一"路径+线宽"抽象，顶点数不同；菱形=旋转 45° 的方，三角=等分 120° 的三点 | 推测，需用不同参数实测确认 |
| 中心线 / 中心框 | 线宽与高度相等时矩形退化成线段（重叠直线） | 确定（说明原文明确） |
| 纹理 / 画笔颜色 | 每个绘制对象独立颜色；纹理为 PNG，程序启动时扫描 `程序目录\纹理\*.png` | 确定（说明原文）+ 高度怀疑（GDI+ 纹理画刷 TGPBrush 子类） |
| 透明合成 | `BitBlt`，光栅操作为 `0x00CC0020`（SRCCOPY），见 `0x5fd644` | 确定 |

### 4.6 输出链路【确定】

- 导出对话框过滤串：`GIF图像|*.GIF|TIF图像|*.TIF|PNG图像|*.PNG|位图|*.BMP|JPG图像|*.JPG`
- **PNG/GIF 才支持透明**（说明原文：要生成透明图章请选 GIF 或 PNG）
- PNG 的 DPI 用用户设定值；GIF 固定 96（GIF 格式本身不存 DPI）
- 预览缩放 1–1000 倍；**导出按实际尺寸，不按预览尺寸**（说明原文强调"图形的最终输出大小按外线设置的大小输出"）
- 抗锯齿三档：传统 / 中质量 / 高质量（对应 GDI+ 的 `SmoothingMode` / `TextRenderingHint`）【高度怀疑】

## 5. 重写映射表（现代技术）

| 原程序 | 建议替代 | 说明 |
|---|---|---|
| VCL + GDI+ | **Canvas 2D（浏览器）/ Skia（桌面）/ resvg（SVG 渲染）** | 抗锯齿与文字渲染质量远超 GDI+；SVG 还能直接给用户矢量文件 |
| DFM + ACCESS 印章库 | **JSON / SQLite** | 参数即 schema，迁移脚本一次性转换 |
| FastReport 设计器/预览/导出 | **自绘预览 + 导出库** | FastReport 只在打印/PDF 场景才有价值；导出 PNG/GIF 自己写更可控 |
| 度→弧度的整数运算 | 全程 `double`，角度存"度"、渲染时转弧度 | 避免"归一化到 [0,360)"带来的舍入抖动 |
| 每字旋转的近似投影 | 标准旋转矩阵 `rotate(a)` | 视觉更正确 |
| 三星/五星硬编码 | 参数化多边形（n 边 + 内外半径比） | 顺手支持七角星、齿轮 |
| 纹理平铺 | Canvas `createPattern` / SVG `<pattern>` | 天然支持任意缩放不失真 |
| DPI 后处理 | 导出时按 `px = mm/25.4*dpi` 一次算定 | 不要"先按 96dpi 画再放大" |

### 5.1 重构骨架（伪代码，仅供理解，不落地）

```ts
type Stamp = {
  frame:  { shape: 'circle'|'ellipse'|'rect'|'diamond'|'triangle',
            w: number, h: number, stroke: number, color: string, texture?: string }
  symbol: { kind: 'star5'|'image', radius: number, sx: number, sy: number,
            dx: number, dy: number, color: string, texture?: string }
  axis:   { stroke: number, h: number, w: number, dx: number, dy: number, gap: number }
  texts:  Array<{ content: string, font: string, charW: number, charH: number,
                  mode: 'flat'|'ring', radius: number, startAngle: number,
                  stepAngle: number, dx: number, dy: number, color: string, texture?: string }>
  out:    { dpi: number, aa: 'low'|'mid'|'high', format: 'png'|'gif'|'bmp'|'jpg'|'tif' }
}

function drawTextRing(ctx, t) {
  const chars = [...t.content]
  const base  = t.startAngle
  for (let i = 0; i < chars.length; i++) {
    const deg = (base + i * t.stepAngle) % 360
    const rad = deg * Math.PI / 180
    // 12 点方向起、顺时针
    const x = cx + t.radius * Math.sin(rad) + t.dx
    const y = cy - t.radius * Math.cos(rad) + t.dy
    ctx.save()
    ctx.translate(x, y)
    ctx.rotate(rad)                 // 字形随角度旋转
    ctx.fillText(chars[i], -charW/2, charH/2)
    ctx.restore()
  }
}

function drawStar5(ctx, s) {
  const rIn = s.radius * Math.sin(Math.PI/10) / Math.sin(3*Math.PI/10)  // ≈0.382R
  ctx.beginPath()
  for (let k = 0; k < 10; k++) {
    const r = (k % 2 === 0) ? s.radius : rIn
    const a = (-90 + k * 36) * Math.PI / 180   // 尖端朝上，每 36° 一个点
    ctx.lineTo(cx + r*Math.cos(a)*s.sx, cy + r*Math.sin(a)*s.sy)
  }
  ctx.closePath(); ctx.fill(); ctx.stroke()
}
```

### 5.2 重构时必须先定死的三件事

1. **坐标系与单位**：mm 还是 px？原程序内部是 px 整数，导致"改 DPI 后线宽会变粗"。建议内部用 mm，渲染时统一乘系数。
2. **"外框"抽象是否保留**：原程序让圆/方/菱形/三角共用一条路径，好处是新增章型几乎零成本；如果新做分支式实现，会丢掉这个优势。
3. **字体依赖**：印章常用宋体/仿宋/黑体，字形宽度决定环排是否闭合。若要做到"字数变了自动撑满整圈"，需要 `Δ = 360 / 字数` 自动模式（原程序是手动填每字角度，可能是痛点）。
